# Hart2Hart Staging VAPT Assessment

**Assessment date:** 2026-11-05  
**Repository:** `Univercitysingle/dating-app`  
**Branch assessed:** `migrate-to-serverless`  
**Environment:** Cloudflare Pages and Workers staging  
**Assessment type:** Source review, deployment-configuration review, and non-destructive automated security tests

## Executive summary

The assessment identified two application authorization gaps, a missing baseline browser security-header policy, a support-attachment authorization-key validation defect, and a staging-to-production CDN trust-boundary concern. Application-level fixes were committed to the migration branch and are being validated by the staging deployment workflows.

The most important unresolved risk is that the staging API Worker uses the `dateme` CDN Worker in its **production** environment and the staging deployment workflow writes the shared `JWT_SECRET` to that production Worker. This allows staging deployment credentials and code to affect the production CDN trust boundary. It requires a separately deployed staging CDN Worker and a separate signing secret.

This is not a full external penetration test. The staging Pages endpoints were not accessible to the browser-based check, and the standalone CDN Worker source and Firebase Realtime Database security rules are not present in this repository.

## Scope and safety

Included:
- Firebase ID-token verification and email-verification enforcement
- Durable Object account-state authorization
- Admin authorization and profile privacy controls
- Photo and support-attachment upload validation
- CDN signing and service-binding configuration
- Rate-limiting configuration
- Payment callback verification logic
- Cloudflare Pages response-header configuration
- GitHub Actions deployment configuration and dependency hygiene

Excluded:
- Destructive account, subscription, payment, or object-storage operations
- Load testing, denial-of-service testing, credential guessing, or password spraying
- Production user data and real user accounts
- Direct testing of the standalone CDN Worker internals, Firebase RTDB rules, Cloudflare dashboard settings, and MongoDB Atlas network/role settings where source or authorized read access was unavailable

## Findings

### VAPT-01: Staging API is coupled to the production CDN Worker

**Severity:** High  
**Status:** Open, requires environment separation

Evidence:
- `wrangler.jsonc` binds staging `CDN_PROXY` to service `dateme`, environment `production`.
- `.github/workflows/deploy-worker-staging.yml` runs `wrangler secret put JWT_SECRET --name dateme`, which writes the staging workflow's secret to the production CDN Worker.
- The staging API Worker also receives the same signing secret in its staging environment.

Impact:
- A compromised staging deployment or staging API runtime can potentially create authorized CDN PUT/DELETE requests against the storage service used by the production CDN Worker.
- A staging deployment can change the production CDN Worker's JWT verification secret.
- Staging and production do not have a strong cryptographic or service-level isolation boundary.

Remediation:
1. Deploy a separate `dateme-staging` CDN Worker.
2. Give it a dedicated staging JWT signing secret.
3. Use a separate staging B2 bucket or a dedicated B2 application key restricted to a staging-only bucket and required operations.
4. Change the staging API service binding and `CDN_HOSTNAME` to the staging CDN Worker.
5. Remove production CDN secret updates from the staging deployment workflow.
6. Verify that staging cannot read, overwrite, or delete production objects.

No change was made to the production CDN service because its source is maintained outside this repository and an isolated replacement cannot safely be deployed from the available repository contents.

### VAPT-02: Central Durable Object guard did not enforce all account restrictions

**Severity:** Medium  
**Status:** Fixed in source, staging deployment validation in progress

Previously, the central Durable Object guard blocked accounts queued for deletion but did not centrally apply the existing `isAccountRestricted` helper. Some individual operations had their own suspension checks, while others did not. The guard also did not require verified email claims for ordinary authenticated operations, although new profile provisioning required a verified email.

Remediation committed:
- Require `email_verified === true` for ordinary authenticated Durable Object operations. The dedicated authentication-verification endpoint remains available in the API Worker.
- Apply `isAccountRestricted` centrally, covering deletion-pending, deleted, permanently banned, and active temporary suspensions.
- Fail closed when a suspension expiry timestamp is invalid.
- Add regression tests for active suspensions, invalid suspension timestamps, unverified identities, and deletion-pending accounts.

### VAPT-03: Baseline browser security headers were not configured in Pages source

**Severity:** Medium  
**Status:** Fixed in source, deployed-header validation in progress

The Pages `_headers` file previously contained crawler directives only for login and registration routes.

Added:
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Strict-Transport-Security: max-age=31536000`
- `Permissions-Policy: camera=(self), microphone=(self), geolocation=(self)`

The deployed SEO validator now checks these response headers on the homepage. A restrictive Content Security Policy was not added because the application's Firebase, WebRTC, and payment flows need a separately tested allowlist.

### VAPT-04: Valid support-attachment keys were rejected by CDN authorization

**Severity:** Low, availability/integrity  
**Status:** Fixed in source, regression deployment validation in progress

The support-key regular expression in `workers/index.js` escaped the dot twice. The valid key format generated by the support upload route uses a normal extension separator, so valid support attachment keys did not match the authorization pattern.

Remediation:
- Corrected the extension separator in the support-key expression.
- Added a regression test that signs a valid ticket-scoped support attachment key and verifies the generated CDN authorization claims.

### VAPT-05: Tracked dependency installation files and incomplete dependency scanning

**Severity:** Medium  
**Status:** Open

The migration branch contains approximately 9,490 tracked paths under `node_modules`, even though `.gitignore` excludes `node_modules/`. The Worker deployment workflow installs dependencies with audit disabled, and no Dependabot or CodeQL workflow was found in the inspected branch workflow inventory. The Worker package also has no committed lockfile.

Impact:
- Committed generated dependencies increase the review and supply-chain attack surface.
- Floating dependency ranges without a committed Worker lockfile reduce build reproducibility.
- Vulnerable transitive dependencies may not be detected promptly.

Remediation:
1. Remove tracked `node_modules` contents from Git while retaining package manifests and lockfiles.
2. Commit a Worker lockfile and use `npm ci` for reproducible installs.
3. Add automated dependency auditing and Dependabot updates.
4. Add CodeQL or equivalent static analysis for JavaScript/TypeScript.
5. Review and remediate dependency advisories before production cutover.

### VAPT-06: External security controls were not independently verified

**Severity:** Assessment limitation  
**Status:** Requires separate verification

The standalone CDN Worker source is maintained outside this repository. Firebase Realtime Database security rules are also not included in the inspected source tree. Therefore this assessment cannot certify:
- CDN JWT algorithm and claim validation, key rotation, origin allowlisting, object ownership checks, or B2 bucket permissions
- Firebase RTDB rules for chat read/write authorization and user-to-user isolation
- Cloudflare dashboard-level WAF, bot, TLS, and rate-limit settings
- MongoDB Atlas network allowlists, database users, and least-privilege roles

These controls should be reviewed directly before production cutover.

## Positive controls observed

- Firebase ID tokens are verified using Google's RS256 signing keys and checked for issuer, audience, expiry, issued-at time, authentication time, and subject.
- Profile provisioning requires verified email for new users.
- Public profile responses use an allowlist and remove private contact fields.
- Photo uploads validate MIME type, file signatures, and a 5 MB size ceiling.
- Support attachments validate MIME type, file signatures, ticket ownership, and a 10 MB size ceiling.
- Photo deletion uses a pending state and finalizes metadata only after CDN deletion succeeds or the object is confirmed absent.
- CDN PUT/DELETE requests are signed and object keys are constrained to application formats.
- Sensitive admin operations use database-backed role checks, with superadmin-only controls for destructive account deletion.
- Payment callbacks verify the gateway signature and validate the documented response structure.
- API smoke tests check that anonymous requests are rejected by migrated authenticated routes.
- The deployment workflows are restricted to `migrate-to-serverless`.

## Validation status

Application changes were committed only to `migrate-to-serverless`. No changes were made to `main`.

The following GitHub Actions runs completed successfully:
- Worker run [42035169211](https://github.com/Univercitysingle/dating-app/actions/runs/42035169211): 228 tests passed, 0 failed; staging Worker deployment, MongoDB readiness, and anonymous-route smoke checks passed.
- Pages run [42034822690](https://github.com/Univercitysingle/dating-app/actions/runs/42034822690): frontend tests, build, Cloudflare Pages deployment, SEO validation, and deployed browser security-header validation passed.

The Worker deployment workflow also completed its step that synchronizes `JWT_SECRET` to the `dateme` production CDN Worker. This confirms the VAPT-01 environment-coupling finding is active, not merely a static configuration concern.

A successful CI run confirms the covered automated checks only. It does not substitute for a live authenticated upload test or the external CDN/Firebase configuration review.

## Production-readiness decision

**Do not treat the environment as fully VAPT-cleared for production yet.**

The staging-to-production CDN coupling (VAPT-01), dependency hygiene/scanning (VAPT-05), and external control verification (VAPT-06) remain open. Complete those items and perform an authorized live DAST assessment against the isolated staging environment before production cutover.
