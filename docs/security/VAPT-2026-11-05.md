## Findings and remediation

### VAPT-01: Staging API is coupled to the production CDN Worker

**Severity:** High  
**Status:** Open, intentionally excluded from this work

The staging API Worker uses the `dateme` CDN Worker in its production environment. The existing staging deployment workflow also synchronizes the `JWT_SECRET` to that production CDN Worker.

Impact:
- A staging deployment can affect the production CDN trust boundary.
- Staging and production do not have separate CDN signing credentials and service boundaries.

This finding was not remediated because CDN work was explicitly excluded. No CDN Worker source, B2 bucket policy, or CDN environment isolation change was made.

**Deployment side effect and current state:** The staging deployment workflow previously synchronized the staging API's `JWT_SECRET` to the production `dateme` CDN Worker. That production-secret write was removed from the staging workflow on 2026-11-05. The workflow now configures the API staging Worker secret only. However, the staging API still uses the production CDN endpoint and a shared signing trust boundary. This remaining coupling is intentionally open and excluded from this assessment.

### VAPT-02: Central Durable Object guard did not enforce all account restrictions

**Severity:** Medium  
**Status:** Fixed and deployed

Previously, the central Durable Object guard blocked accounts queued for deletion but did not centrally apply all account restrictions.

Remediation:
- Require `email_verified === true` for ordinary authenticated Durable Object operations.
- Apply the shared account restriction helper centrally, covering deletion-pending, deleted, permanently banned, and active temporary suspensions.
- Treat invalid suspension expiry timestamps as restricted.
- Add regression tests for active suspensions, invalid expiry values, unverified identities, and deletion-pending accounts.

### VAPT-03: Missing or overly broad browser security policy

**Severity:** Medium  
**Status:** Fixed in source and deployed

Added and validated:
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Strict-Transport-Security: max-age=31536000`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy` limited to the app's camera, microphone, and geolocation requirements
- A restrictive Content Security Policy with explicit API, Firebase, CDN, Cloudflare Insights, and media sources
- Same-origin CORS policy for Pages static resources
- `Cross-Origin-Resource-Policy: same-origin`
- `Cross-Origin-Opener-Policy: same-origin-allow-popups`

The Pages deployment validator now checks the deployed CSP and cross-origin response headers. The CSP avoids broad scheme-wide source allowances. Inline style attributes remain permitted for the existing React UI; inline scripts and `unsafe-eval` are not allowed.

### VAPT-04: Support attachment CDN key validation rejected valid keys

**Severity:** Low, availability  
**Status:** Fixed in source and deployed

Corrected the support attachment key extension expression and added a regression test that verifies a valid ticket-scoped support attachment key produces the expected signed CDN claims.

### VAPT-10: NoSQL operator injection through admin support-ticket status filters

**Severity:** Medium  
**Status:** Fixed in source and regression-tested

The legacy admin support-ticket listing previously copied the request's `status` query value directly into a MongoDB filter. An object such as `{ "$ne": "Closed" }` could therefore reach the query builder. The admin status-update endpoint also accepted non-string status values.

Remediation:
- Accept only string values present in the SupportTicket schema's status enum.
- Reject object/operator values with HTTP 400 before querying or updating MongoDB.
- Bound pagination values and cap page size at 100.
- Add regression tests for operator objects in both the listing filter and status-update body, including verification that the stored ticket status remains unchanged.

Validation: backend regression tests passed in [Cloudflare Pages pipeline run 42068156222](https://github.com/Univercitysingle/dating-app/actions/runs/42068156222). The full staging deployment and fresh Pages ZAP scan are tracked by that same run.

### Firebase session and password-setup review update (2026-11-05)

### Admin authorization and superadmin session review (2026-11-05)

**Finding:** The superadmin login endpoint minted a Firebase custom token for the fixed UID `superadmin_uid` with a server-assigned `superadmin` custom claim. However, the shared authentication middleware only provisioned database users, and the Firebase custom-token identity could fail database provisioning because it does not use verified-email account linking. This made the superadmin login and subsequent admin authorization path inconsistent.

**Remediation:** The authentication middleware now recognizes the exact fixed UID only when the verified Firebase ID token also contains the server-assigned `role: superadmin` claim. It creates a minimal request-scoped superadmin principal and bypasses ordinary user provisioning and subscription lookup. A role claim on any other UID does not receive this exception. Firebase ID-token signature and revocation checks still run before this branch.

**Authorization middleware:** Role checks now validate both configured role lists and the authenticated principal's role against the application's fixed role set. Invalid middleware configuration fails closed with HTTP 500; missing, malformed, or insufficient roles are denied with HTTP 403. Denial logging uses structured request logging and no longer writes UID/URL strings directly to the console.

**Regression coverage:** Tests in `tests/authenticationMiddleware.test.js` cover the fixed superadmin UID plus signed claim, rejection of a superadmin claim on another UID, malformed bearer headers, and Firebase revocation. Tests in `tests/adminSecurityValidation.test.js` cover invalid role configuration, admin denial on superadmin-only routes, and superadmin access. The backend regression suite passed these tests in [Cloudflare Pages run 42072198850](https://github.com/Univercitysingle/dating-app/actions/runs/42072198850).

**Security condition:** The fixed superadmin UID is safe only while custom-token issuance remains exclusively server-side and the credential check in the login handler remains protected. Keep the superadmin password hash in a secret, rotate it if exposed, and never accept a role from request body or client profile data.

Full VAPT clearance remains pending. No legacy backend deployment was performed.

### IDOR and privilege-escalation review update (2026-11-05)

**Admin account creation privilege escalation:** The admin user-creation controller validated requested roles against the schema but did not restrict creation of the `superadmin` role to an already authenticated superadmin. An administrator could therefore request creation of a new superadmin account. The controller now rejects this request with HTTP 403 unless `req.user.role === 'superadmin'`. A regression test was added to `tests/adminSecurityValidation.test.js`.

**Profile photo ownership and mass-assignment:** The profile update endpoint previously accepted the `photos` field, and the photo-order endpoint replaced the entire stored photo array with client-provided objects. This allowed a user to inject arbitrary photo keys or alter stored photo metadata without using the authenticated upload flow. The general profile update allowlist no longer accepts `photos`. The photo-order endpoint now requires the submitted list to contain exactly the existing photo keys, once each, and rebuilds the array from server-stored photo records, preserving ownership and metadata. Regression tests were added to `tests/usersController.test.js` for foreign-key injection and metadata tampering.

**Route ownership and input validation:** User support-ticket detail and message operations scope ticket lookup by both ticket ID and authenticated user ID. User and admin ticket detail/status routes reject malformed ObjectIds before database access. Ticket creation requires a 1-150 character subject and a 1-5000 character message; user/admin replies are type-checked and capped at 5000 characters. Admin support-ticket routes are protected by Firebase authentication and admin/superadmin role middleware. User report submission is mounted under the authenticated API router.

**Verification:** Backend regression tests in `tests/usersController.test.js`, `tests/userUtils.test.js`, `tests/supportTicket.test.js`, and the admin security suites passed in [Cloudflare Pages run 42072198850](https://github.com/Univercitysingle/dating-app/actions/runs/42072198850). No live IDOR test was performed against staging, no database data was changed, and no legacy backend deployment was performed. Full VAPT clearance remains pending.

### Profile data disclosure review update (2026-11-05)

**Finding:** The shared `sanitizeUser` helper returned the complete user object to profile owners and superadmins, including the stored password hash. For other viewers it removed email and mobile number but retained internal account metadata such as last login IP/device, password-setup state, block lists, and suspension timestamps.

**Remediation:** Password hashes are now removed for every viewer, including the profile owner and superadmins. Public profile responses additionally omit email, mobile number, last login IP/device, initial-password setup state, block lists, and suspension timestamps. The shared helper is used by profile and other user-response paths, so this closes the common serialization path rather than relying on individual route fixes.

**Regression coverage:** Tests in `tests/userUtils.test.js` for owner/superadmin password-hash suppression and public-profile metadata suppression passed in [Cloudflare Pages run 42071732479](https://github.com/Univercitysingle/dating-app/actions/runs/42071732479).

**Outstanding purchase consistency risk:** Purchase approval currently marks a purchase completed before applying the user's entitlement update. If the entitlement update fails, the purchase can remain completed without the purchased entitlement. The earlier conditional status update prevents duplicate approvals but does not make the two database writes atomic. This requires a transaction or an idempotent entitlement ledger before this flow can be considered safe. No transaction change was made without verifying the staging MongoDB transaction topology.

No staging deployment or live user-data modification was performed. Full VAPT clearance remains pending.

### Payment and subscription request review update (2026-11-05)

Source-level review identified weaknesses in payment-order creation and status lookup. Remediations committed:

- Store item IDs and subscription plan identifiers are checked as primitive strings against server-side catalogs; client-supplied prices are not used.
- Payment gateway configuration and the HTTPS frontend return URL are checked before creating a pending order.
- Subscription payment currency is restricted to the configured LKR catalog currency.
- Existing pending subscriptions are no longer deleted automatically when a user starts another payment attempt, avoiding destruction of an order that may still receive a valid provider response.
- Purchase and subscription status endpoints reject malformed MongoDB ObjectIds before querying.
- Added focused tests in `tests/paymentInputValidation.test.js`.

Important unresolved payment risks:

- **Callback cryptography mismatch:** The [official WebXPay redirect guide](https://developers.webxpay.com/Guides/Redirect-Integration/redirect.html) and its [PHP response sample](https://developers.webxpay.com/Guides/Redirect-Integration/php-response.txt) describe base64-decoding `payment` and `signature`, applying public-key decryption to the signature, and comparing the decrypted signature bytes with the payment bytes. The current legacy callback instead uses NodeRSA `verify()` configured for `pss-sha1`. This does not match the published sample and must be confirmed against the merchant's current WebXPay integration profile before reuse.
- **Callback order parsing and status:** The official guide identifies the first field as the merchant `order_id` and the second as the gateway order reference. The current controller selects the second field when it starts with `T`, then uses it as a MongoDB document ID. It also does not validate the gateway success status before marking purchases completed or subscriptions active. The guide itself is inconsistent about whether status code is field 4 or 5, so the exact field order must be confirmed with WebXPay. Only status `0` or `00` is documented as approved; status `15` is declined.
- **Server-to-server verification:** WebXPay publishes a [Transaction Retrieval API](https://developers.webxpay.com/APIs/Transaction-retreval-API/retreval-api.html) with lookup by gateway order reference or merchant order ID, authenticated using API credentials and a bearer token. The callback does not currently use this API to independently verify transaction status and amount before granting entitlements.
- **Replay and atomicity:** The callback updates purchase/subscription state and user entitlements in separate writes. Concurrent callback delivery can duplicate increments, while partial failure can leave a completed payment without its entitlement. This needs an idempotent transactional or recoverable design after the Atlas transaction topology is verified.
- Existing `tests/subscription.test.js` is skipped. The backend regression suite in [Cloudflare Pages run 42072198850](https://github.com/Univercitysingle/dating-app/actions/runs/42072198850) completed successfully, including the new payment input validation tests. The skipped subscription suite remains a coverage gap.
- No payment gateway transaction was initiated and no payment callback code was changed or deployed.

These payment callback issues are high priority. The current code is legacy Express source and is not evidence of a secure payment callback in the Cloudflare Worker application.
